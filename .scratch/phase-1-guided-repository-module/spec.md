## Problem Statement

A programmer who can write small TypeScript programs can still struggle to understand how an unfamiliar repository implements a feature across routing, handlers, services, and persistence. Reading files individually does not explain how the components cooperate, which state changes, why repeated actions preserve existing state, or how to make and validate a small change independently.

The learner needs a coherent, trustworthy teaching journey through one real workflow, with enough context to reason about it and practice locally. They also need to know which explanations are supported by source and execution evidence, which are engineering interpretations, and what their practice results can actually establish. A complete repository course, an account, and a live bot should not be prerequisites for that first experience.

## Solution

Deliver one free, anonymous, English-language preview module based on tele-bot's `/start` registration and welcome workflow at **fixed source revision `14f5af8f5ff31149552c0403c32b261cb1a95cc0`**. The motivating question is: why does sending `/start` again use the existing Wallet rather than recreate it or reset its Available Balance?

A minimal catalog entry leads to an introduction and five freely navigable, problem-first lessons. Readable source excerpts, exact source links, a recurring workflow diagram, explained self-checks, and a bounded trade-off discussion connect the problem to actual behavior. One reference-assisted prediction exercise provides immediate prepared feedback. A local assignment asks learners to personalize only the new-Buyer welcome and write regression tests, with verified setup instructions, acceptance criteria, staged hints, and a separately available reference solution.

By the end of the module, the intended outcomes are to trace the connected workflow, predict new/returning/changed-username behavior, explain state preservation and one registration-local trade-off, and make and locally validate the bounded greeting change. These are learning objectives, not established learner proficiency.

Prepare and review content outside the application. Distribute only an exact, explicitly approved course release through the agreed manual static-preview process. Keep implementation readiness, creator publication approval, human evaluation, and learning effectiveness separately identifiable.

## Implementation Decisions

1. **Deliver one bounded increment.** Build the anonymous learner journey, its prepared content, browser exercise, local-assignment materials, and external creator workflow together. Phase 1 contains one module from one teaching repository. tele-bot's marketplace is context; `/start` registration and welcome is the teaching boundary. Instruction is in English. Original source and reply excerpts retain their fidelity to the pinned repository, with explanation where necessary.

2. **Preserve the selected learner and four objectives.** Require basic TypeScript functions, objects, types, `async`/`await`, simple tests, and Git. Prior framework knowledge is not required. The learner should be able to trace the workflow; predict the three registration scenarios; explain Wallet preservation and the bounded trade-off; and make and locally validate the greeting change. Do not promise independent implementation of the whole bot.

3. **Separate reusable delivery from repository-specific content.** Provide reusable catalog, introduction, lesson/navigation, source-excerpt, diagram, prepared-exercise, and assignment rendering responsibilities. Repository names, workflows, domain terms, examples, ordering, and the first module's five lessons are content. Do not encode tele-bot or a universal five-lesson count as the platform model. No additional course is required to demonstrate this separation.

4. **Use version-controlled prepared content with explicit contracts.** Store explanations and assignment instructions as Markdown, with structured metadata and exercise data compiled at build time. The content contract must represent release identity separately from fixed source revision; repository and discovery metadata; ordered lessons and stable lesson/section links; objectives and prerequisites; exact source references; evidence classifications and disclosures; diagram references; and the exercise and assignment materials. Exercise data must identify the three scenarios, their three separately evaluated parts, allowed choices, accepted choices, per-choice feedback and source references, optional hints, and worked explanations. Validate required identity, references, ordering, and choice/feedback relationships during preparation/build so incomplete or inconsistent content cannot silently become a distributable candidate. Parser, dependency versions, physical layout, and schema syntax are implementation choices within this contract.

5. **Use the agreed static architecture.** Use Next.js and TypeScript with static export for catalog, introduction, lessons, excerpts, and assignment. Compile the content at build time and provide the prepared exercise through a Client Component with browser-only, unsaved state. Phase 1 needs no runtime application server, learner-record database, or remote evaluation endpoint. Answers and feedback shipped to the browser may be inspected; this is compatible with reference-assisted practice and a separately revealed explanation.

6. **Provide discovery and free navigation.** The catalog card identifies tele-bot, the motivating `/start` problem, target learner, and limited preview. Its introduction supplies purpose, technologies, architectural context, complexity, prerequisites, four objectives, expected outcomes, and available lessons. Start learning opens the first lesson. Every published lesson remains directly accessible through the lesson list, previous/next links, and direct lesson/section links. Practice is reached through Apply the understanding and links back to relevant explanations. State that progress and results are not saved. Readiness self-checks never lock access.

7. **Implement the agreed teaching progression as content.** Use five lessons without another chapter layer:

   | Lesson | Required teaching and readiness behavior |
   | --- | --- |
   | Predict the behavior | Introduce the bot's purpose, the repeated-`/start` problem, Buyer–Wallet relationship, and new/returning scenarios. Explain the self-check distinguishing Buyer identity from Wallet and Available Balance before tracing. |
   | Follow the command | Connect update → routing → handler → registration service → persistence → reply. Explain responsibilities, relevant inputs/outputs, Telegram updates, and dependency wiring. Check understanding of who receives identity, registers the Buyer, and constructs the reply before persistence details. |
   | Explain state preservation | Explain changed usernames, Buyer/Wallet relationships, uniqueness, transactions, and conflict handling. Check what changes and what remains unchanged when registration repeats. |
   | Reason about the trade-off | Explain registration-local state preservation and PostgreSQL-specific insertion detection, then briefly compare an explicitly returned registration outcome in a hypothetical alternative persistence design. |
   | Apply the understanding | Present the bounded browser exercise, then the local change. Before local practice, invite a trace and justification of all three scenarios, with an explanation available. |

   Explain the new-Buyer case fully; invite returning-Buyer and changed-username predictions before revealing explanations. Revisit one workflow diagram connecting components, new/returning branches, and the Buyer–Wallet relationship. Introduce unfamiliar concepts when needed. Acknowledge the Admin branch and missing-sender guard without teaching administration. The sequence is educational reconstruction, not an asserted development chronology.

8. **Pin the source and keep the walkthrough self-contained.** Every excerpt identifies the exact file and relevant lines/section and links to the full approved commit, using commit-permalink line anchors where available. Place readable excerpts beside connected explanations. External source links supplement the teaching. Show course release, full fixed source revision, and preview scope on the introduction, with compact identity accessible from each lesson. A changing default branch must not change the module's evidence basis.

9. **Use the pinned behavior as the scenario contract, subject to recorded execution.** Prepare exercise wording, source explanation, and feedback against these outcomes:

   | Scenario | Required state prediction | Required reply prediction |
   | --- | --- | --- |
   | New Buyer | Create one Buyer and its Wallet with zero Available Balance. | Use the pinned implementation's generic new-Buyer welcome, Wallet-creation confirmation, initial balance, and Buyer menu. |
   | Returning Buyer | Reuse the existing Buyer and Wallet without duplicate creation or resetting Available Balance. | Use the returning-Buyer welcome and current balance, with the existing display-name preference. |
   | Returning Buyer with changed username | Persist the changed username while preserving Buyer identity, Wallet identity, and existing nonzero Available Balance. | Remain in the returning-Buyer branch, showing the current balance and the name selected by the existing preference. |

   Supporting explanations connect the relevant handler, service, repository, and constraints rather than merely restating the prediction. Keep the browser exercise anchored to original behavior; the greeting assignment deliberately changes that behavior locally. Source inspection supports this contract, but required execution evidence remains pending. Do not infer unconditional transaction support from a comment: explain the service's transaction-capable path and executor fallback accurately without implying a broader guarantee.

10. **Keep criticism proportional to evidence.** Teach that uniqueness and conflict handling support repeated-registration identity and Wallet preservation, while new-versus-existing detection uses PostgreSQL-specific `xmax`. Present portability implications as engineering interpretation, not a verified defect, a portability guarantee, or the developer's proven original rationale. The alternative explicit registration outcome is hypothetical. No replacement implementation, `xmax` internals, or advanced concurrency analysis is required. Distinguish source-supported facts, verified defects, potential risks, engineering interpretations, hypothetical scenarios, proposed improvements, and educational reconstruction beside affected passages. Genuine-history claims require specific evidence; disclose material uncertainty and gaps.

11. **Implement one bounded prediction exercise.** For each of the three scenarios, accept only provided selections for Buyer/Wallet state, reply behavior, and supporting explanation. Evaluate the three parts separately on submission using prepared criteria. Confirm correct reasoning, explain the misconception for an incorrect choice, and link relevant source evidence. A correct prediction with an incorrect explanation receives mixed feedback. Do not compute an overall score or award proficiency. Lessons, diagram, and excerpts remain available; there is no timer or mandatory pass gate.

12. **Make exercise response states explicit.** Missing selections remain unanswered, with completed parts evaluated and unanswered parts identified. Invalid or unsupported selections require reselection without an educational judgment. Selections remain editable after feedback, but edits require resubmission; do not present feedback for the previous selection as an evaluation of the edited answer. Offer optional source-directed hints, unlimited retries, a fresh-attempt reset, and a separately revealed worked explanation. Revealing an explanation does not fill unanswered parts or establish proficiency. Do not persist attempts, histories, progress, or results.

13. **Prepare the authentic local assignment and assistance.** Starting from the pinned revision, personalize only the new-Buyer welcome using the existing name preference: trimmed first name, otherwise `@username`, otherwise the generic greeting. Scope learner edits to the welcome handler and its tests. Preserve Wallet-creation confirmation, displayed initial balance, Buyer keyboard, registration, and Admin/returning-Buyer behavior. Provide context, desired behavior, exact fixed-revision references, acceptance criteria, and validation guidance. Learners choose the implementation and write regression tests themselves. Offer staged hints and a separately revealed reference solution; the main instructions do not walk through the implementation. Ask for a final diff review and a brief self-reviewed explanation of preserved behavior.

14. **Make local validation reproducible before distribution.** Verify dependency installation, dedicated disposable PostgreSQL provisioning, explicit test configuration, and a passing baseline at the pinned revision. The inspected source declares Node >=22.13.0 and npm >=10.0.0, with npm@10.0.0 specified and a lockfile; record the exact tested environment and commands in the assignment materials. Focused tests still run global setup and migrations, and their helpers truncate tables and can fall back to development/default database URLs. Explicitly select the isolated disposable test database rather than relying on fallback configuration. Required checks must work without a live Telegram account, real bot token, or Wallex access; live Telegram testing is optional.

   Assignment acceptance requires all name/fallback cases, including first-name precedence when both names exist, trimming, whitespace-only first name with username fallback, and generic fallback when neither supplies a name. New personalization assertions must fail against the original generic greeting and pass after the change; generic-fallback assertions should already pass and remain passing. Preserve observable Wallet confirmation, initial balance, and keyboard. Run the existing `/start` tests, registration tests, and type checking. Distinguish setup failure, an unexpected baseline failure, and a new failure after editing. Supply troubleshooting and staged assistance; do not advise weakening assertions. Results and explanations remain local, self-reviewed, and unverified by the platform.

15. **Carry source-verification and rights obligations into release preparation.** Before distribution, record actual checks for new registration and initial Wallet creation, repeated registration without duplicate identity/Wallet, username persistence, and Wallet identity/nonzero-balance preservation, including the combined changed-username case. Use the isolated disposable database and record the exact source revision and environment. Keep any additional verification harness or test overlay traceable to the pinned source; it must not silently change the source revision taught. The combined-case gap is creator preparation work, not a defect proven by missing tests or a required extension of the learner's greeting assignment. Record the creator's authorization to reuse controlled tele-bot material, source excerpts, and practice materials, and review third-party rights and attribution separately. Do not represent that authorization as an independently verified ownership chain or public repository license.

16. **Keep creator review and publication external.** The creator owns preparation, final publication approval, and distribution verification. Maintain one external candidate review record linking release identity, immutable content reference, full fixed source revision, rights evidence, exact source references, actual verification results, separate technical and educational reviews, reviewers, findings, and their disposition. Review technical correctness, objectives, lesson coherence, answer choices/feedback, local guidance, and claim sufficiency. Agents may assist; the creator may conduct both reviews, and an independent reviewer is optional. Missing rights, required behavior evidence, or material technical/educational findings blocks distribution. Minor findings require a rationale and any necessary learner-visible limitation. Automated passes and agent reviews do not constitute creator publication approval.

17. **Approve the complete exact artifact before preview distribution.** Finish the entire local static deployment package, including routes and headers, before local review, checksumming, and approval. The exported site alone is not the final Vercel Build Output API package. Record the readable course-release identifier, immutable content/content commit, full source revision, build environment, complete artifact checksum, approved preview scope, and dated explicit creator publication approval. Include only learner-facing content and assets in the distributed package; exclude drafts and internal review records. Use a dedicated Vercel preview project disconnected from Git, with automatic publication from pushes disabled. After approval, manually upload the approved package using prebuilt deployment without rebuilding. Before distribution, verify agreement between candidate, findings, scope, and approval; afterwards record the actual date, location, and package agreement. A mismatch stops distribution until corrected.

18. **Provide an anonymous, unlisted preview with verified operations.** Share a stable, release-specific learner address with invited evaluators rather than an immutable deployment permalink. Apply noindex controls and verify actual anonymous access, protection settings, indexing controls, project access, and account permissions. Anyone obtaining the address may access or forward it; invitation and noindex do not enforce a restricted audience. A provider production target may serve this preview without constituting public V1 launch. Verify that the account and delivery arrangement can publish the exact artifact and withdraw every hosted copy before distribution. If those requirements cannot be met, revisit the arrangement rather than weakening them.

19. **Preserve stable releases and support withdrawal.** Draft changes invalidate affected review results; recheck affected evidence and approve the final snapshot. Revised published teaching, major corrections, newer source revisions, and expanded preview curricula require a separate course release, review, and approval. Earlier releases remain identifiable; future learner records remain associated with the version studied, without implementing records or migration here. Withdrawn approval or a new blocking finding stops distribution: serve a notice at the stable release entry, remove affected retained deployments and aliases, delete separately retained immutable assets where applicable, and verify former entry, lesson, data, deployment, alias, and asset URLs no longer serve the withdrawn materials. Preserve identity, evidence, artifact, and withdrawal reason internally. A replacement links to a separately approved release; unchanged restoration requires recorded resolution and renewed approval.

20. **Track completion with actual evidence.** The creator owns the Phase 1 evaluation record, with agents assisting in preparation and technical checks. Record actual course release, full source revision, content commit, artifact checksum, environment, evaluated address, evaluator, date, reproducible steps, expected/observed results, and outstanding findings. Separately identify implementation checks, human walkthrough observations, publication approval, and optional formative observations. Phase 1 delivery completion requires an approved available preview, recorded results across all five roadmap criteria, and no unresolved finding materially obstructing or misrepresenting the journey. Guide readiness and automated passes leave human evaluation pending until observations are reported. Neither bounded acceptance nor optional formative observations establishes measured learning effectiveness or broader proficiency.

## Testing Decisions

- **Confirmed primary seam:** test the built static site's anonymous learner journey through its visible pages, links, and exercise controls. The creator confirmed this seam in this session. Prefer this single application-level seam to introducing separate public test interfaces for navigation, Markdown rendering, or answer evaluation. Exercise outcomes should be checked through what the learner selects and sees. Supporting build/content checks, teaching-source verification, and operational evidence address boundaries that the browser alone cannot establish.
- **What makes a good test:** arrange a meaningful learner scenario, perform supported actions, and assert observable content, links, state/reply predictions, and feedback. Use independently reviewed expected outcomes grounded in the pinned source; do not derive expected correctness by calling the same evaluator or blindly copying an unchecked answer mapping. Avoid assertions about component internals, private helpers, exact layout snapshots, or incidental markup. A source-link assertion verifies its revision and intended evidence, not merely that an anchor exists.
- **Application responsibilities covered:** catalog/introduction and fit information; freely accessible lesson and section navigation; rendering of connected content, excerpts, diagram, and evidence disclosures; practice links; the prepared exercise; and readable assignment/assistance materials. Test direct lesson loading as well as navigation from the catalog, using a fresh anonymous browser with no account or saved learner state. Check the built output rather than relying only on a development server.
- **Prior art:** this repository currently has planning documents and skills, with no application, package manifest, or existing application test suite. There is no in-repository browser-test precedent to extend. In the teaching repository, the pinned [start-handler tests](https://github.com/h3nrzi/tele-bot/blob/14f5af8f5ff31149552c0403c32b261cb1a95cc0/tests/bot/buyer/start.test.ts) exercise replies, persisted state, and synthetic updates with intercepted outgoing messages; the [registration-service tests](https://github.com/h3nrzi/tele-bot/blob/14f5af8f5ff31149552c0403c32b261cb1a95cc0/tests/modules/buyer/registration.service.test.ts) check identity, Wallet creation/reuse, and username persistence through real PostgreSQL. Reuse these existing source/assignment seams rather than adding repository-level interfaces solely for tests. They have been inspected, not executed in this specification effort.
- **Exercise coverage:** for each of the three scenarios, exercise every supported choice for state, reply, and explanation and inspect intended prepared feedback and source links. Include correct prediction with incorrect explanation, fully unanswered and partially answered submissions, invalid/unsupported values, hints, worked-explanation reveal, edits requiring resubmission, repeated attempts, and reset. Feedback must preserve the distinction among correct, incorrect, unanswered, and unsupported. Verify no overall score, proficiency claim, access gate, saved result, or explanation reveal that silently completes unanswered parts. It is unnecessary to enumerate every Cartesian combination once independent dimensions and mixed feedback are covered.
- **Content integrity:** check required metadata and choice/feedback completeness, valid lesson ordering and internal references, exact source revision in permalinks, and fidelity of excerpts to their identified source. Technical review verifies that the source actually supports each explanation and that disclosures are sufficient. Human educational review evaluates coherence, gradual reduction of guidance, diagram usefulness, and the interpretation/hypothesis boundaries; a passing link checker cannot establish those qualities.
- **Teaching-source behavior:** run the existing relevant handler and registration tests against the fixed revision using an explicitly selected disposable database. Add a traceable verification check for changed username combined with a seeded nonzero Wallet balance, asserting persisted username, unchanged Buyer/Wallet identities and Available Balance, no duplicate rows, and returning reply behavior. Record actual results and environment; leave unperformed or failing checks visibly pending. Do not connect to an implicit development database or treat inspection as a passing run.
- **Assignment preparation:** actually follow the supplied setup instructions from the fixed revision, establish the baseline, and execute the bounded change using the prepared validation guidance. Demonstrate expected regression failures for new personalization assertions, passing behavior after the change, unchanged fallback behavior, preserved reply content/keyboard, and passing existing `/start`, registration, and type checks. Review that the reference solution stays within the handler/test boundary. This preparation verifies actionable instructions without turning learners' local results into platform-verified outcomes.
- **Package and operational checks:** inspect the complete candidate for unintended drafts/review records, record its checksum and build environment, and confirm that the uploaded artifact matches the approved package without a rebuild. Verify anonymous preview access and noindex behavior at the actual distributed address. Rehearse and record withdrawal against former deployment, alias, lesson, data, and immutable-asset URLs using authorized non-teaching test material where possible before distributing teaching material. Provider capability documentation is not evidence that the actual account procedure succeeded.
- **Reproducible human evaluation:** after implementing each ticket and completing its required checks and review, prepare the feature-by-feature evaluation guide and actual preflight evidence using the required global ticket-walkthrough skill in the implementation chat. Preserve checkpoints per ticket and provide the first concrete action. This handoff work does not add an unrequested implementation-approval gate. Human evaluation remains pending until the user reports observations.

No account, payment, or mandatory pass gate intervenes. | Actual evaluated address/release, steps, expected and observed access/navigation behavior. |

Review the diagram, self-checks, and decreasing guidance. | Named technical/educational review findings and actual walkthrough observations; coherence is not inferred from page existence. |

Source and evidence integrity | Compare excerpts and references with the full fixed revision and inspect affected claim labels, uncertainty, and reconstruction framing. | Exact references, recorded behavior checks, and review of claim sufficiency; unsupported history and defect claims remain blockers. |
| 4. Browser and local practice | Exercise correct/incorrect/unanswered/unsupported responses, mixed reasoning, assistance, retries, editing, and reset. Actually perform the local assignment with its setup and validation guidance. | Observed feedback and links, reproducible local execution results, and explicit limits on verification/proficiency. |

External publication traceability | Trace the distributed release back to rights, source, reviewed content, complete package, explicit approval, and final distribution check. | Release/content/source identities, build environment, checksum, rights/review records, dated creator approval/scope, actual location and package agreement. |

## Out of Scope

- Accounts, saved progress, personal profiles, assessment histories, saved local results, objective-level proficiency reports, adaptive recommendations, personalized paths, and remedial/advanced branching. These are later-phase capabilities.
- A complete first course, additional modules/courses, required video/audio support, downloadable books/packaging, formal cohort validation, success thresholds, accreditation, or public V1 launch. Optional formative observations remain separate from learning-effectiveness evidence.
- Teaching purchasing, payment processing, Top-Ups, administration, framework internals, advanced concurrency, a full architecture survey, or every source file. The selected trace acknowledges its guards/branches without expanding into those topics.
- Changing registration services, schemas, databases, or test infrastructure as part of the learner greeting assignment; implementing the hypothetical persistence alternative; or requiring learners to repair the creator's combined-case evidence gap.
- Learner repository submissions, embedded course generation or arbitrary repository analysis, live AI instruction, generated explanations/exercises, arbitrary code/free-form evaluation, cloud development environments, submissions or a routine human-grading service.
- A complete in-app repository browser, dedicated authoring/publication dashboard, user-generated publishing, marketplace/community/collaboration features, public evidence portfolios, monetization, multilingual instruction, or a universal course-mastery badge.
- Automatic source synchronization, lesson regeneration, progress migration, offline interactive application, answer secrecy, or tamper-resistant grading.
- Implementation tickets, application scaffolding, lesson manuscripts, exercise banks, assignment solutions, infrastructure changes, deployment execution, and creator publication approval as outputs of this specification task. They are subsequent implementation/preparation or explicitly authorized release work.
