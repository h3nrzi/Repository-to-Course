# 09: Rehearse anonymous preview delivery and withdrawal

**What to build:** Demonstrate on the actual authorized hosting account that an exact static package can be published anonymously at a stable release-specific address and completely withdrawn. Use authorized non-teaching test material so this independent rehearsal establishes operational feasibility before any course release is distributed.

**Blocked by:** None (can start immediately).

**Status:** ready-for-agent

- [ ] Establish authorization and required account/project access for the actual rehearsal actions and non-teaching test material. Planning approval alone is not authorization to distribute teaching material or change an external account; record unavailable access or permission explicitly.
- [ ] Use a dedicated Vercel preview project disconnected from Git, with automatic publication from pushes disabled. Record actual account permissions, protection settings, and the procedure used rather than relying on provider capability documentation alone.
- [ ] Prepare the complete local deployment package, including static output, routes, and headers, and record its checksum and build environment before manual prebuilt upload. Verify the rehearsed procedure uses that package without rebuilding.
- [ ] Establish a stable release-specific test entry rather than asking evaluators to depend on an immutable deployment permalink. Verify actual anonymous access in a fresh browser and actual noindex controls at the hosted address.
- [ ] State that an unlisted invitation and noindex do not enforce a restricted audience: anyone obtaining the address may access or forward it. A provider production target may serve the preview without making it public V1 launch.
- [ ] Inventory the rehearsal's hosted copies and entry, lesson, data, deployment, alias, and immutable-asset URLs, including retained prior deployments or separately retained assets where applicable.
- [ ] Actually rehearse withdrawal: stop distribution, serve a notice at the stable entry, remove affected deployments and aliases and separately retained assets, and verify former URLs no longer serve the test material. Record checks and account actions with actual results.
- [ ] Document how internal release identity, evidence, artifact, and withdrawal reason are retained; replacements reference a separately approved release. Unchanged restoration requires recorded resolution and renewed creator publication approval.
- [ ] Rehearse or concretely verify the controls needed to keep different course releases identifiable and to invalidate affected review/approval after draft or artifact changes. Do not use a rebuild or replacement package under an old approval.
- [ ] If the actual arrangement cannot support exact-artifact publication, anonymous access, and complete withdrawal, record the finding and revisit the arrangement before teaching distribution; do not weaken the release requirements or claim feasibility from documentation.
- [ ] Review the operational evidence, then complete the global ticket-walkthrough handoff with reproducible steps, actual preflight results, and the creator's first action. Human evaluation and course-release approval remain separately pending.
